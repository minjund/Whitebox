# 첫 응답 검증과 연속 분석

근거 보호와 요청 범위를 유지하면서 형식 재시도를 줄이는 실험이다.
이전 보완안에서 재시도가 발생한 조건은 미확인 항목을 적고도 주의 문구를
비운 경우, 미확인 항목이 남았는데 완료로 표시한 경우였다.

생성 지침에서 필요한 미확인 사실을 먼저 정하고 행동·복잡도를 고르게 했다.
미확인 항목이 있으면 비어 있지 않은 주의 문구와 verify 또는 허용된
continue를 함께 작성해야 한다. 완료를 얻으려고 미확인 사실을 지우지 않는다.
미해결 조건이나 여러 단계가 있는 작업은 standard를 사용하고, 기존 글자 수
한도 안에서 필수 항목을 먼저 배치한다. 완료 시 빈 행동 필드를 유지하며,
후속 지시는 decision.action.request에만 생성한다. 앱이 이미 nextStep을
그 필드에서 계산하므로 별도 중복 생성은 필요하지 않다.

근거 선택기, 요청 범위 지침, assessDecision 검증 함수는 이전과 같다.
판정을 사후 수정하거나 미확인 항목을 버리지 않고, 검증 한도와 최대 2회
모델 호출도 유지한다. 첫 응답과 최종 응답의 성공을 별도로 센다.

## 연속 분석 오류

사용자가 보고한 시점의 앱 저장 내용에서 분석 응답 형식 오류를 확인했다.
해당 요청은 잠금 전 영수증 조회 이유를 묻는 요청이었다. 당시 실패한 분석
응답 원문과 실패 모델은 저장되지 않아 원인을 확정할 수 없다. 그 후 캐시가
바뀌었으므로 정확한 원래 대화의 요청 ID로 입력만 복원했다.

별도 재현 시험에서는 Claude의 중간 assistant 문장 뒤에 명시적 최종 result가
도착했는데 앱이 중간 문장을 반환하는 문제가 확인됐다. 터미널 검토 경로는
명시적 최종 result를 전달하도록 수정했다. 잘못된 최종 JSON을 이전 초안으로
대체해 성공시키지 않으며, 일반 작업·질문지 처리 경로는 바꾸지 않는다.
이 문제가 당시 오류와 같은 원인이었다고 단정하지 않는다.

다음은 제어된 응답으로 실제 서비스·수신 코드를 시험한 회귀 검사다.

- 최종 result만 있거나 중간 문장 뒤 최종 result가 오는 수신 30회
- 서로 다른 6개 세션의 대기열과 최대 한 개 모델 호출 유지
- 같은 요청 재분석 20회와 매번 연속 클릭 5회의 중복 호출 방지
- 한 세션에서 서로 다른 완료 요청 20개가 분석 대기열에 쌓이는 경우
- 잘못된 JSON의 명시적 오류, 다른 세션의 진행, 수동 재시도 후 복구
- 응답·요청 혼입, 이전 응답 재사용, 리스너 누적, 비공개 실행 파일 생성 방지

## 실제 모델 비교 설계

기존 9개 사례는 같은 Sonnet 5.5로 각 방식 3회, 실제 오류 입력은 Opus 5.5로
각 방식 3회 실행한다. 추가 모델은 같은 터미널의 직전 저장 분석에 나타난
모델이며 실패 당시 모델의 증거로 취급하지 않는다. 합계 최종 분석 60개이며
모든 응답을 새로 생성한다. 원래 9개 보완 전 프롬프트는 이전 보완안과
바이트 단위로 같다. 원문 입력도 두 방식에서 같다.

각 호출을 CLI 직접 호출 대신 실제 앱의 AgentRunner에 통과시킨다. 하나의
runner와 비공개 작업 폴더를 연속 재사용하며, CLI는 매번 새 실행이고 세션
저장·도구·사용자 대화 재개를 끈다. 최종 CLI 결과와 앱에 전달된 문자열의
해시를 대조하고 실제 모델 ID, 종료 상태, 사용량, 수신 시간, 잔여 실행을
기록한다. 수신 경로 수정은 두 방식에 공통이므로 프롬프트 효과와 별도로
재현 회귀 검사로 검증한다.

주요 지표는 첫 응답 통과율, 형식 재시도와 추가 근거 복원 횟수, 최종 오류,
재시도 포함 건당 평균·중앙값·p90·최대 지연, 캐시 포함 입력·출력 토큰이다.
p90은 관측 표본의 nearest-rank이며 모델이 다른 집단의 지연은 별도로
보고한다. 형식 통과를 의미 정답률로 세지 않는다. 원문 구간 보존, 수정 요청
확대, 조건부 수정 허용, 최신 금지와 불확실성 보존도 함께 확인한다.

이것은 설치 앱의 UI 클릭 E2E가 아니다. 제어된 대기열 검사와 실제 모델
수신 검사를 구분하며, 당시 응답 원문이 없는 오류의 재현 성공을 주장하지
않는다. 모델·네트워크 변동과 작은 실제 사례 수 때문에 일반적인 향상률로
해석할 수 없다.

## 결과

최종 분석 60개, 재시도 포함 실제 모델 호출 64회를 수행했다. 앱에 전달된
64개 문자열이 각각 CLI의 최종 result와 일치했다. 수신·파싱 오류와 도구
호출은 0회였으며 각 성공 뒤 남은 실행도 0개였다.

기존 9개 Sonnet 사례를 방식별 27회 분석한 결과는 다음과 같다.

| 항목 | 보완 전 | 보완 후 |
| --- | ---: | ---: |
| 첫 응답 형식 통과 | 23/27 | 27/27 |
| 형식 재시도 | 4 | 0 |
| 최종 형식 통과 | 27/27 | 27/27 |
| 건당 평균 | 9.14초 | 7.66초 |
| 중앙값 | 8.29초 | 7.94초 |
| p90 | 16.95초 | 8.90초 |
| 최대 | 19.03초 | 9.86초 |
| 입력 토큰, 캐시·재시도 포함 | 182,890 | 164,043 |
| 출력 토큰, 재시도 포함 | 29,567 | 24,293 |

평균은 16.3%, p90은 47.5% 줄었다. 보완 전 재시도는 조건부 수정 사례
3개(빈 주의 문구 2개, 총 글자 수 초과 1개)와 반복 로그 사례 1개(원문에
없는 이유 인용)였다. 보완 후에는 같은 검증 규칙으로 첫 응답이 통과했다.

추가 Opus 실제 오류 입력은 방식별 3회 모두 첫 응답이 통과했다. 평균은
20.22→23.18초로 14.7% 늘었으므로 이 모델에서 속도 개선은 확인되지
않았다. 모델이 다른 60개 분석을 합치면 평균은 10.25→9.21초지만, 이를
모델별 속도 개선으로 해석하지 않는다.

동일한 지정 원문 입력 16개 구간을 양쪽 모두 보존했다. 검증·원인 보고·
설명 전용 12개 응답에서 수정 지시는 없었다. 조건부 수정의 continue와
최신 수정 금지도 각각 3/3 유지됐다. 원인 미확인은 후보의 주의 문구에
남았지만 unverified 배열은 비었으므로 같은 JSON 필드에 보존된 것은
아니다. 수정 요청을 완료로 바꿔 처리하지는 않았다.

문체·판단 전체가 동일하거나 개선됐다고 단정할 수는 없다. 조건부 수정
2개 응답에는 실패 보고만 하고 마치는 불필요한 가정적 대안이 있었다.
주 실행용 후속 지시는 수정으로 유지됐지만 대안 관련성은 불안정했다.
Map 통제 사례는 호출과 공유 함수의 연결 설명이 부족하다. 후보 2/3은
그 한계를 주의 문구에 표시했고 1/3은 표시하지 않았다. Opus 3회차는
구현 미확인의 한계를 주의 대신 verification에 적었다. 형식 통과를 의미
정확도나 경고 표시의 일관성으로 세지 않는다.

독립적인 블라인드 평가는 아니다. 작은 표본의 실제·합성 요청과 모델·
네트워크 변동이 포함돼 있으며, 원래 사용자의 실패 응답 원문은 없어
당시 오류의 동일 원인을 확인하지 못했다. 소스의 수신 경로 수정과 연속
회귀 검사를 통과한 사실, 새 모델 호출에서 오류가 없었던 사실을 구분한다.

## 실행

```sh
node scripts/terminal-review-sequential-test.js
node scripts/terminal-review-hybrid-test.js
node scripts/terminal-review-hybrid-refined-test.js
npm run test:result-review
npm test
npm run check:source
node scripts/terminal-review-first-pass-benchmark.js artifacts/terminal-review-first-pass-20261102 --prepare-only
node scripts/terminal-review-first-pass-benchmark.js artifacts/terminal-review-first-pass-20261102
node scripts/terminal-review-first-pass-benchmark.js artifacts/terminal-review-first-pass-20261102 --render-only
```

처음 준비할 때 이전 보완 실험의 corpus·prepared와 변경 전 프롬프트
템플릿이 필요하다. 이후에는 새 폴더의 고정 corpus를 재사용한다. 코드,
자료, 프롬프트 해시가 달라지면 기존 결과를 재사용하지 않는다. 모델 오류나
파싱 실패는 성공으로 세지 않고 보존한다. 같은 입력을 임의로 재호출하여
좋은 응답만 고르지 않는다.

원문·사용량·재시도와 최종 보고서는 무시되는
`artifacts/terminal-review-first-pass-20261102/`에 남긴다. 입력 보호와
검증 규칙의 동일성은 `invariants.json`, 오류 입력의 출처·불확실성은
`observed-error.json`, 수정 전 수신 재현은 `sequential-before-fix.log`로
확인할 수 있다. 버전업이나 배포는 이 작업에 포함하지 않는다.
