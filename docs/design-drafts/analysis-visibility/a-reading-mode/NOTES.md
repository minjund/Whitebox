# A — 읽기 모드

## 산출물과 사용법

- `index.html`: 외부 CDN·폰트·런타임 없이 여는 정적 HTML. 기본 화면은 **결과 도착 / 미읽음 / 터미널 2개**다. 테마는 OS의 `prefers-color-scheme`을 따르며 상단에서 시스템·다크·라이트로 바꿀 수 있다.
- `dark.png`, `light.png`: 1440×900, 읽기 모드를 유지하며 ONE_ONLY 도크에 입력하는 상태. 액센트 테두리와 “입력 중” 표시를 포함한다.
- `analyzing-dark.png`: 같은 크기의 분석 중 화면, 터미널 2개.
- `grid-three-dark.png`: 분석 중 화면, 터미널 3개.
- `capture.cjs`: 저장소에 이미 설치된 Electron으로 캡처와 동작 검증을 재현하는 보조 스크립트. 새 패키지를 설치하지 않았다.

URL 쿼리도 지원한다. 예: `index.html?theme=light&state=analyzing&count=3`. `mode=terminal`은 결과가 도착한 뒤에도 터미널 중심으로 보는 화면이다. 쿼리는 새로고침할 때의 초기 조건이며 UI 조작이 URL에 저장되지는 않는다.

상단 44px의 상태·테마·터미널 수 선택은 **시안 비교용 컨트롤**이다. 실제 제품에는 헤더의 읽기 모드 토글만 둔다. 사이드바의 검색·패널 추가·설정은 배치 확인용이며 동작하지 않는다.

## ① 분석이 더 잘 보이는 이유

평소에는 `220px 사이드바 | 넓은 터미널 그리드 | 280px 이해·검토`를 유지한다. 결과가 도착하면 사이드바는 그대로 두고 `중앙 분석 | 344px 터미널 도크`로 역할을 바꾼다. 결과를 읽으라는 상태 문구와 패널의 위치 변화가 함께 도착을 알린다.

1440×900에서 중앙 패널은 808px, 내부 본문 컨테이너는 720px이고 좌우 20px 패딩을 제외한 **실제 본문 폭은 680px**다. 본문은 15px/1.8, 짧은 소제목은 13px, 결론은 25px다. 상태색은 도착 표시와 권장 행동에 제한하고, 주의는 별도 황갈색으로 남긴다. 색상·간격의 출발점은 `renderer/styles-terminal-workspace.css`의 `--wb-*` 토큰과 220px 사이드바다.

본문은 **결론 → 이유 2개 → 주의 → 권장 행동 버튼 1개 → 접힌 상세** 순서다. ONE_ONLY, “문서 생성은 보고됐지만 본문은 확인되지 않았습니다.”, 페이지 ID와 본문 확인의 구분, 백업→SQL→확인의 순서는 브리프의 기존 화면을 따른다. 추가한 확인 요청은 시안의 제안이며 실제 문서 검증 결과가 아니다. 원문 기준·시간·토큰은 하단으로 보냈다. 상세의 `docker compose ps`는 기존 화면의 기록으로만 표시하며 문서 본문 확인의 증거로 취급하지 않는다.

행동 버튼과 상세 펼치기 행은 둘 다 첫 화면 안에 들어온다. 메타데이터까지 보려면 조금 스크롤할 수 있다. 내용을 늘리거나 작은 창을 쓸 때는 중앙 본문만 스크롤한다.

## ② 상태별 동작과 복귀

| 상태 | 배치와 동작 |
| --- | --- |
| 아직 작업 없음 | 제품 구현 시 터미널 중심을 유지하고 우측에 간단한 안내를 둔다. 이번 목업에는 별도 시나리오가 없다. |
| 분석 중 | 터미널 중심. 우측은 현재 분석 대상 ONE_ONLY와 진행 안내를 보여 준다. |
| 결과 도착·미읽음 | 입력을 방해하지 않는 시점에 중앙 읽기 모드로 전환. “결과 도착”, “새 분석”을 표시하고 터미널 출력은 오른쪽 도크에 남긴다. 이후 입력을 시작해도 읽기 배치를 유지한다. |
| 읽음 | 본문에 포인터를 누르거나 키보드 포커스를 넣으면 읽음으로 바뀐다. 토글·단축키로 명시적으로 읽기 모드에 진입해도 읽음 처리한다. 단순 도착이나 도크 입력만으로 읽었다고 간주하지 않는다. |
| 읽기 모드에서 입력 | 보호할 포커스나 본문 선택이 없으면 인쇄 가능한 키·Backspace·Enter·한글 조합 시작을 ONE_ONLY 입력란으로 보낸다. 도크 본문 클릭도 입력란 포커스만 옮긴다. 배치는 그대로이고 도크 테두리를 액센트로 강조하며 “입력 중”을 표시한다. 포커스가 떠나면 강조와 표시를 지운다. |
| 오류 | 제품 구현 시 자동 배치 전환 없이 터미널 중심 유지. 유효한 이전 결과가 있으면 오류 안내와 함께 남긴다. 이번 목업에는 별도 오류 시나리오가 없다. |

터미널 모드로 돌아가는 방법은 **도크 상단 확대 버튼, 헤더 토글, ⌘/Ctrl+.** 세 가지다. 도크 본문 클릭과 키 입력은 복귀 동작이 아니다. 읽기 모드를 유지하면서 도크 입력란으로 포커스만 옮긴다. 권장 행동으로 초안을 준비해도 읽기 모드를 유지한다.

일반 키의 `keydown`에서 먼저 입력란을 포커스하고 **동일 textarea와 브라우저 기본 입력 동작을 유지**한다. 첫 글자를 수동으로 재전송하지 않아 중복 입력을 피한다. IME의 `Process`/229·Dead 키도 조합 시작 전에 포커스를 옮긴다. 이미 비편집 영역에서 시작된 `compositionstart`는 입력란으로 포커스를 옮기고, 원래 대상에서 이어지는 조합 갱신·종료 데이터로 같은 구간을 교체해 한글 중간 상태·확정·취소를 보존한다. 입력란 자체의 네이티브 조합은 브라우저에 맡긴다.

본문에 명시적으로 포커스가 있거나 버튼·링크·폼·편집 가능 영역·상세 펼치기·사용자 지정 포커스 요소를 조작 중이면 입력을 가로채지 않는다. 선택한 본문이 있을 때와 기존 단축키도 보호한다. **Tab/Shift+Tab은 가로채지 않고 기존 DOM 순서 그대로** 둔다. 도크 입력란은 기존 순서로 접근할 수 있고 입력 대상과 확대 방법을 접근성 설명에 포함했다. 포커스 진입 시 “ONE_ONLY 도크 입력란입니다. 읽기 모드를 유지합니다.”를 알린다. 포커스가 터미널에 있거나 조합 중에 새 결과가 오면 현재 배치를 유지하고 도착만 알리는 보호도 유지한다.

배치 전환은 기존 요소의 위치를 기준으로 **180ms 이동·페이드**한다. `prefers-reduced-motion: reduce`에서는 Web Animations 실행과 CSS 전환을 모두 끈다. 분석 도착 때 본문으로 포커스를 강제로 옮기지 않는다. 스크린리더에는 짧은 상태만 `aria-live="polite"`로 알린다.

“본문 확인 요청 준비”는 **읽기 모드를 유지하며 도크에 초안만 붙이고 입력란을 포커스**한다. 기존 입력이 있으면 두 줄을 띄워 덧붙인다. 자동 제출하지 않으며, 이 정적 목업에서 Enter는 줄바꿈이고 명령이나 요청을 실행하지 않는다.

### 터미널이 2~3개인 경우

- 터미널 모드: 2개는 좌우 그리드, 3개는 ONE_ONLY를 왼쪽 전체 높이에 두고 나머지를 오른쪽 위·아래에 둔다. 돌아갈 때 이 구조와 각 입력값을 유지한다.
- 읽기 모드: **결과를 읽는 ONE_ONLY만 344px 도크에 남긴다.** 다른 1~2개를 이 좁은 폭에 다시 분할하지 않는다. 도크 아래에 이름·대기 상태를 담은 목록을 둔다. 사이드바 목록도 유지한다.
- 읽기 모드에서 다른 터미널 행을 클릭하면 확대 버튼으로 그리드를 여는 방법을 안내하고 배치를 유지한다. 위 세 가지 명시적 복귀 방법으로 그리드를 연 뒤 다른 터미널을 선택하면 해당 입력란에 포커스를 준다. ONE_ONLY 행은 도크 입력란을 포커스한다. 기존 ONE_ONLY 분석은 대상 라벨을 유지한다. 이번 목업의 분석 데이터와 도크 대상은 ONE_ONLY 고정이므로, 다른 터미널의 새 분석을 생성하거나 도크 대상을 바꾸는 기능은 없다.
- 실제 구현에서는 원래 분할 트리·비율·스크롤 위치·포커스·선택 대상의 식별자를 저장한다. 읽기 모드를 나갈 때 복원하고, 다른 터미널의 결과가 도착해도 현재 읽는 분석을 덮어쓰지 않는다. 출력은 계속 버퍼링하되 백그라운드 터미널에는 상태·미읽음 수만 표시한다.

## ③ affectUI 참고 범위

2026-11-05 공식 문서를 확인했다. **무료 MIT만 사용**한다는 브리프 조건을 우선했다.

- [smart-recommendation](https://www.affectui.com/components/smart-recommendation): 공식 문서에 무료 MIT로 표시. 얇은 테두리의 추천 카드, 이유와 행동을 나눈 작은 하단 영역, 절제된 상태색을 참고했다. 제품의 증거 수준과 혼동할 수 있는 신뢰도 막대는 사용하지 않았다. React 컴포넌트는 설치·복사하지 않고 CSS로 직접 작성했다.
- `renderer/vendor/affectui/button-clean.tsx`: 저장소의 무료 clean 버전. 단색 주요 버튼·미세한 테두리와 그림자·보조 동작의 낮은 강조를 참고했다. 원본의 긴 모핑 시간은 옮기지 않았다.
- `renderer/vendor/affectui/segmented-control-clean.tsx`: 저장소의 무료 clean 버전. 회색 트랙·활성 칩·동일한 글자 굵기를 상단 시안 컨트롤에 적용했다. 여기서는 `aria-pressed`를 가진 일반 버튼 그룹으로 구현했다.
- [app-shell](https://www.affectui.com/screens/app-shell), [approval-card](https://www.affectui.com/components/approval-card): 요청받은 참조 페이지는 읽었지만 현재 공식 문서가 **Pro**로 표시하므로 구성요소 코드·레지스트리·스타일을 가져오지 않았다. 쉘은 기존 Whitebox 3단 배치에서 직접 구성했고, 행동 카드는 위 무료 smart-recommendation을 참고했다. 승인·거절 기능도 추가하지 않았다.

외부 서비스 호출, 이미지, 웹 폰트, 유료 코드 의존성은 없다.

분석을 처음 띄울 때와 새 결과 도착 때를 분리하고, 읽는 도중 새 결과가 오면 자동 교체를 막아야 한다. 도착 중 입력·조합·텍스트 선택·드래그를 보호할 필요가 있다. 너비 변경 후 PTY resize가 잦아지지 않도록 실제 fit은 최종 레이아웃에서 모아서 처리한다.

1200px 아래에서는 본문 폭이 점차 줄고 도크는 320px, 980px 아래에서는 280px로 줄어든다. 760px 아래 목업은 사이드바를 숨기고 세로로 쌓는다. **640~720px 본문 + 320~380px 도크 + 사이드바를 모두 보장하는 기준은 데스크톱 1440×900**이다. 좁은 창의 최종 제품 정책은 추가 결정이 필요하다.

## ⑤ 약점

1. 빈 영역에서 타이핑해도 도크로 입력되므로 사용자가 입력 대상을 오인할 수 있다. 액센트 테두리·“입력 중”·접근성 안내를 넣고 본문 선택과 상호작용 포커스를 보호했지만, 실제 스크린리더 사용성은 검증하지 않았다.
2. 읽기 배치를 유지하는 대신 좁은 도크에서 긴 입력과 로그를 편집해야 한다. 다른 터미널의 자세한 출력이나 넓은 편집이 필요하면 확대 버튼·토글·단축키로 명시적으로 전체 그리드를 열어야 한다.
3. 이 시안은 ONE_ONLY 고정 분석과 정적 출력이다. Chromium 조합 엔진과 합성 이벤트는 확인했지만 실제 운영체제 한글 IME·후보창, 스트리밍, PTY resize, 다중 분석 경합은 검증하지 않았고 좁은 창에서는 기준 본문 폭이 줄어든다.

## 실행한 검증

저장소의 기존 `scripts/terminal-workspace-check.js` 등에 있는 `BrowserWindow` / `capturePage()` 방식을 참고해 전용 캡처 스크립트를 작성했다. 제품 전체 테스트는 실행하지 않았다.

```sh
node --check docs/design-drafts/analysis-visibility/a-reading-mode/capture.cjs
```
