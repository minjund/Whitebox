# B — 오른쪽 패널이 시선을 벌게 한다

산출물: `index.html`, `dark.png`, `light.png`, `thinking-dark.png`.
외부 CDN·새 패키지 없이 동작하는 단일 HTML 목업이다. 기준 화면은 1440×900이며 상단의 시안 조작부에서 상태와 테마를 바꿀 수 있다. 실제 PTY·분석 API와 연결하지 않았다.

## ① 이 배치가 분석을 더 잘 보이게 하는 이유

- **3단 구조 유지:** 1440px에서 사이드바 220px | 터미널 812px | 검토 패널 408px이다. 작업 중과 결과 도착 시 모두 폭을 고정해 입력 영역이 갑자기 움직이지 않는다. BRIEF의 280px보다 128px 넓으며, 좌우 여백 24px를 제외한 본문 공간은 약 359px다. 참고로 현재 소스의 CSS 폴백은 280px이지만 `terminal-workspace.js`의 초기·복구 기본값은 332px다. 실제 적용 시 두 기본값을 함께 맞춰야 한다.
- **첫 내용은 결론:** 패널 제목 다음에 결론 카드가 오고, ONE_ONLY·이번 요청·오후 09:00 메타는 카드 아래의 작은 한 줄로 내려갔다. 결론을 찾기 위해 메타와 탭을 지나갈 필요가 없다.
- **읽기 순서:** 결론 → 이유 2개 → 확인 범위와 남은 점 → 권장 행동 1개 → 접힌 기록이다. 본문은 15px/1.8, 결론은 21px/1.55다. 본문 최대 폭은 680px로 제한하지만 이 안의 실제 본문은 패널 폭 안에서 읽는다. 60~70자를 채우려는 설계가 아니다.
- **연결된 도착 신호:** 사이드바 ONE_ONLY 행의 점 → 해당 터미널 헤더의 ‘결과 도착 →’ → 패널 왼쪽 액센트 바와 ‘새 결과’ 필로 같은 결과를 연결한다. 도착 때만 결론 카드가 한 번 부드럽게 강조된다.
- **시선의 종착점:** 채워진 primary 버튼은 ‘본문 확인 요청 준비’ 하나다. 버튼 위에 권장 행동과 그 이유를 두어 무엇을 할지 이해한 뒤 누르게 한다. 토큰 사용량과 원문 기록은 접힌 상세에 둔다.

## ② 상태별 동작과 터미널 복귀

| 상태 | 표시와 동작 |
| --- | --- |
| 아직 작업 없음 | 기타 상태 메뉴에서 볼 수 있다. 작업 시작 안내와 터미널 이동만 표시한다. 도착 표시는 없다. |
| 분석 중 | 작은 중립색 로더 필, 짧은 안내, 정적인 골격만 표시한다. 큰 민트색 카드나 도착 바가 없어 터미널 입력이 우선한다. |
| 결과 도착·미읽음 | 왼쪽 3px 액센트 바, ‘새 결과’ 필, 사이드바 점, 터미널 헤더 배지가 함께 나타난다. 결론 카드 강조는 1,200ms 동안 1회다. 도착 자체는 포커스를 옮기지 않는다. |
| 읽음 | 패널 본문 클릭·실제 스크롤·휠 조작·키보드 포커스 진입 시 전환한다. 바·필·점·배지가 함께 사라지고 헤더에 작은 ‘읽음’ 문구가 남는다. 결론과 본문은 유지한다. |
| 오류 | 오류와 다시 분석 버튼을 표시한다. 다시 분석은 분석 중 화면으로 이동한다. 실제 오류 복구 API는 연결하지 않았다. |

사이드바 ONE_ONLY 행, 터미널 헤더 배지, 중앙 상단 검토 아이콘은 패널 본문으로 포커스를 이동시키고 읽음 처리한다. 패널의 ‘터미널로 돌아가기’와 패널 내부 Escape는 ONE_ONLY 입력란으로 포커스를 돌린다. 도착 당시 입력 중인 터미널의 포커스는 유지한다.

‘본문 확인 요청 준비’는 수정 가능한 초안 대화상자를 연다. 복사 후 사용자가 터미널에 붙여 넣는 흐름이다. 클립보드 접근이 실패하면 내용을 선택하고 수동 복사를 안내한다. 정적 목업의 터미널 입력은 실제 명령을 실행하지 않는다.

`prefers-reduced-motion: reduce`에서는 결론 강조와 로더 회전을 모두 끈다. 도착 상태는 정적인 바·문구·점으로 계속 전달하며, `aria-live="polite"`로 결과 도착을 알린다. 테마 ‘자동’은 `prefers-color-scheme`을 따른다.

시안 조작부의 ‘결과 도착’을 다시 누르면 새로운 도착을 재현한다. 실제 제품에서는 단순 렌더링·테마 변경·탭 재선택으로 강조를 재생하면 안 된다. 결과 식별자가 바뀐 경우에만 새 미읽음을 만들어야 한다.

### 도착 색으로 `--wb-accent`를 선택한 근거

다크 `#98d4b9`, 라이트 `#28745d`라는 기존 Whitebox 토큰을 재사용했다. 별도 알림색을 추가하면 기존 작업 공간의 색 체계에 또 다른 의미를 외워야 한다. 기존 민트색을 세 위치에 반복하고, 넓은 면 전체를 채우지 않고 바·점·필에 집중하면 작은 신호를 연결할 수 있다.

이 색은 ‘성공’이 아니라 **결과가 도착했음**을 나타낸다. 예시 결론 자체가 본문 확인이 안 됐다는 내용이므로 성공 체크나 승인 문구는 사용하지 않았다. ‘새 결과’와 ‘결과 도착’ 문구를 함께 두어 색만으로 상태를 구분하지 않는다. 읽은 후에는 큰 도착 신호를 없애되 권장 행동 버튼의 기본 강조색은 유지한다.

터미널 표면은 라이트 테마에서도 검정이다. 따라서 터미널 내부에만 `--wb-accent: #98d4b9`를 유지해 배지 대비를 확보했다. 사이드바와 검토 패널은 각 테마의 토큰을 쓴다. 동일한 의미의 민트색을 표면 밝기에 맞게 조정한 것이다. 기존 선택·연결 상태에서도 이 토큰을 쓰므로 도착 표시와 혼동할 가능성은 남는다.

## ④ 실제 구현 시 건드릴 파일과 위험

이 산출물은 제품 코드를 변경하지 않는다. 실제 적용 시 예상 범위는 다음과 같다.

- `renderer/styles-terminal-workspace.css`: 검토 폭 폴백, 결론 카드·도착 바·필·공유 배지, 읽음 표현, reduced-motion, 테마별 대비를 구현한다. 좁은 화면에서 터미널 최소 폭 및 기존 리사이즈 동작과 충돌할 수 있다.
- `renderer/terminal-workspace.js`: `reviewWidth` 초기값과 저장값이 없을 때의 복구값을 조정하고, 검토 마크업·`renderReview()`의 결론/메타 순서를 바꾼다. `acceptReview()`에서 유효한 새 결과가 수락되는 시점과 읽음 이벤트를 연결한다. 사용자 저장 폭은 일괄 덮어쓰지 않는 편이 적절하다.
- 같은 파일의 사이드바·터미널 헤더 렌더링: 세 위치가 동일한 결과 식별자로 미읽음을 표시하도록 연결한다. 기존 `acknowledgeCompletion()`은 터미널 작업 완료 표시를 다루므로 분석 결과 읽음과 무조건 합치면 안 된다. 터미널 입력만으로 아직 보지 않은 분석이 읽음 처리될 수 있다.
- 기존 `scripts/terminal-workspace-layout-test.js`, `scripts/terminal-workspace-check.js`: 실제 렌더러 적용 후 폭·포커스·결과 교체·읽음 동기화·축소 화면·테마 검증을 추가할 후보이다. 이 작업에서 제품 테스트를 실행하거나 수정하지 않았다.

미읽음 키는 터미널 생성 식별자와 분석 결과 식별자를 포함해야 한다. 선택하지 않은 터미널의 결과가 늦게 도착할 때 현재 패널을 덮어쓰거나, 과거 결과 열람이 최신 결과까지 읽음 처리하지 않도록 해야 한다. 테마 전환·폴링·재렌더링으로 펄스가 반복되지 않아야 한다. 읽음은 사용자의 조작을 나타낼 뿐 내용 이해를 보장하지 않는다.

초안은 1200px 미만에서 사이드바 190px·검토 380px로 줄이고 중앙 보조 터미널을 숨기는 단순 반응형 처리를 쓴다. 3단 구조 자체는 유지하지만, 실제 제품에서는 보조 터미널을 접근 가능한 탭으로 전환하는 등 별도 설계가 필요하다. 800px 미만은 최소 폭과 가로 스크롤에 의존한다. 패널 리사이즈, 다중 결과 보관, 히스토리 탭, 실제 자동 분석 설정은 이 목업 범위에 없다.

### 실제 수행한 확인

기존 `scripts/terminal-workspace-check.js`의 Electron `capturePage()` 방식을 참고해 설치된 Electron으로 로컬 목업을 렌더링했다. 새 패키지는 설치하지 않았다. 실행 명령은 다음과 같다.

```sh
node_modules/.bin/electron docs/design-drafts/analysis-visibility/b-right-pane-attention/capture.cjs
```

최종 실행에서 1440×900 캡처, 패널 408px, 본문 15px/27px, 클릭·실제 스크롤·휠·포커스 진입 시 읽음, 배지 동기 해제, 도착 시 기존 입력 포커스 유지, 초안 대화상자 열기, 터미널 복귀, 분석 중·오류·빈 상태, 시스템 다크/라이트 추종, reduced-motion에서 강조·로더 애니메이션 해제, 1280/1024px에서 문서 가로 넘침 없음을 assertion으로 확인했다. 포커스 검증은 DOM API 기반이며 실제 키보드 입력 전체를 자동화한 검증은 아니다. 세 PNG를 열어 육안으로도 확인했다.

처음 두 캡처 시도는 검증 기준과 스크롤 조건에서 실패했다. 패딩을 포함하는 너비 기준으로 고치고, 실제 넘침이 있는 상세 열림 상태에서 스크롤을 검증한 뒤 최종 실행이 통과했다. 내용이 짧아 넘침이 없을 때도 휠 조작으로 읽음 처리하도록 보완했다. PNG는 최종 실행 결과다. 실제 서비스 연동·사용자 시선 이동·이해 속도·접근성 전체를 입증하는 검증은 아니다.

## ⑤ 이 안의 약점

1. **터미널 공간의 비용:** 408px 검토 폭은 두 터미널을 나란히 쓸 때 긴 출력 줄을 더 자주 접는다. 작은 화면의 보조 터미널 접근 방식도 추가 설계가 필요하다.
2. **도착색의 의미 중복:** 기존 민트색이 선택·연결·primary에도 쓰인다. 문구와 일시적인 도착 바가 있어도 익숙해지면 시선을 충분히 끌지 못할 수 있다.
3. **읽음 판정의 한계:** 우연한 클릭·휠·포커스 진입도 읽음으로 처리된다. 실제로 결론을 읽고 이해했는지는 알 수 없으며, 다중 터미널에서 결과별 읽음 보존은 제품 구현으로 검증해야 한다.
