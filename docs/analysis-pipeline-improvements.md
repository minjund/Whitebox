# 작업 분석·협업·질문창 개선 (2026-10-27)

## 확인한 실패 경로

- 분석과 질문지 생성이 같은 내부 CLI 실행 슬롯을 사용했다. 질문지가 아직 실행 중이면 분석 시작이 즉시 거절되어 검토 오류가 됐다. 이제 슬롯이 사용 중이면 대기열에 남는다. 슬롯 종료 이벤트가 다음 분석을 시작한다.
- 터미널 분석은 상태 조회마다 기본 `get(id)`를 사용해 필요하지 않은 재생 버퍼까지 전송받았다. 분석 경로의 조회를 `get(id, false)`로 변경했다.
- 협업 동기화는 구성원마다 원격 `get`을 순서대로 호출했다. 호스트의 소켓 요청 큐가 셸 생성 등으로 지연되면 주기적인 명부 조회도 30초 제한에 걸릴 수 있었다. 주기 동기화는 상태 이벤트로 갱신되는 명부 캐시를 읽는다. 실제 입력 직전에는 원격 실행 식별자와 출력 시퀀스를 다시 확인한다. 재현 테스트는 원격 조회가 막힌 상태에서도 동기화의 원격 조회 횟수가 0임을 확인한다.
- 화면에서 패널 변경과 정기 갱신이 별도 협업 동기화를 만들었다. 진행 중인 동기화 Promise를 공유하도록 바꿨다.
- 분석 갱신 루프의 예외 처리는 현재 선택한 터미널을 오류로 표시했다. 이제 각 터미널의 호출 안에서 오류를 처리해 오류를 일으킨 터미널에 연결한다.
- 관찰·대기 상태도 모두 ‘분석중’으로 표시했다. 화면은 작업 관찰, 분석 대기, 근거 준비, 모델 분석을 구분한다.

로컬 Whitebox와 이전 LoadToAgent 프로필에는 `terminal-reviews.json`이 없었다. 따라서 실제 사용자 환경의 실패율이나 가장 빈번한 오류를 계량한 결과는 없다. 위 내용은 코드와 재현 테스트에서 확인한 경로이다. Codex CLI 0.164.0, Claude Code 2.1.226의 필요한 실행 옵션도 로컬 도움말로 확인했다. 도움말 시작 시간은 모델 분석 지연의 측정값으로 취급하지 않았다.

## 원문과 맥락을 다루는 구조

`terminalReviewCompletion`은 이미 해당 프로세스에 연결한 대화 로그를 읽으면서 공개 사용자 발언, 공개 답변, 도구 결과의 바이트 위치와 해시를 색인한다. 비공개 추론과 도구 호출 인수는 재조회 본문에서 제외한다. 색인에는 위치·해시·짧은 발췌가 있고 원본은 기존 로그에 남는다.

각 참조는 파일 inode, 요청 ID, 바이트 범위와 SHA-256을 가진다. 요청에 속한 `e3` 같은 참조를 통해 구간을 읽으며, 같은 대화에서 연결된 이전 요청의 확인 결과는 이전 요청 ID를 붙여 전달한다. 다른 요청의 참조는 허용된 이전 요청 목록에 있을 때만 재조회한다. 파일이 바뀌거나 없어지면 `changed-or-unreadable`, `expired`로 반환한다. 읽기 한계는 `limit`, 범위 밖 참조는 `out-of-scope`다.

처음에는 현재 요청의 중요 기록 최대 4개를 준비한다. 긴 결과의 앞뒤 외에 삭제·실패·복구 등의 원문 구간을 보존한다. 이전 요청의 중요한 확인 결과도 별도 영역에 둔다. 모델이 누락된 구간을 구체적인 참조로 요구할 때만 최대 4개, 합계 8,000자의 추가 읽기를 수행한다. 재조회 후 분석과 형식 보정을 합쳐 모델 호출은 최대 2회다. 기존 무호출 기록 판정과 동일 근거 중복 방지는 유지한다.

사용자가 제약이나 변경을 말한 요청은 원문과 요청 ID로 별도 보존한다. AI 답변은 그 사용자 기록에 합치지 않는다. 사용자 기록은 시간 순서를 유지하고, 오래된 조건과 철회·변경 발언을 함께 제공한다. 이전 확인 결과의 역할과 요청 ID를 유지해 현재 실행의 결과와 구분한다.

한계도 있다. 최초 로그 읽기는 최대 32 MiB, 참조 색인은 파일당 4,096개, 사용자 조건 기록은 32개이며 화면 분석 입력에는 최근 조건 12개를 축약해 전달한다. 넘친 수와 건너뛴 바이트를 기록한다. 중요 구간 선별은 휴리스틱이며 모든 중요도를 보장하지 않는다. 재시작 후 색인은 원본 로그에서 다시 만든다.

## 판단과 비용

분석은 기록의 이익과 실제 손실을 연결하고, 요구사항 근거·사용처·삭제 안전성을 구분한다. 이전 확인과 상충하거나 범위가 달라졌을 때만 재확인의 차이를 설명하도록 입력을 구성했다. 일반적인 누락 표시만으로 경고나 추가 유료 보정 호출을 강제하던 검사는 제거했다. 실제 미확인 요구사항에 대한 경고와 조기 완료 방지는 유지한다.

완료된 다른 요청은 대기열에서 지우지 않고, 같은 요청의 대기 근거만 최신 내용으로 합친다. 직접 분석 요청과 보고 있는 터미널을 우선하되, 3회 우선 처리 후에는 대기 시간으로 선택한다. 분석 동시 실행 수는 1이다.

작업 판단 대상, 큐 진입, 시작, 근거 준비, 프로세스 시작, 첫 stdout, 결과 수신, 검증, 게시, 화면 표시 시간을 기록한다. 입력 길이, 호출 수, 재조회 수·분량과 토큰 사용량도 저장한다. 계측 레코드는 시각과 수치로 구성된다. 결과는 `terminals:review-state` 이벤트로 전달해 다음 2.5초 폴링을 기다리지 않는다.

## Jev 플러그인과 가로 질문창

설정의 **Jev 플러그인**에서 API 키를 저장한 후 **분석 서비스 → Jev**를 선택한다. 키는 Electron `safeStorage`로 암호화하고 POSIX에서 권한 0600 파일에 원자적으로 저장한다. Windows에서는 사용자 프로필 ACL 안에 암호문을 저장한다. 렌더러 저장 데이터에는 키를 넣지 않으며 저장 직후 입력란을 비운다. 연결 해제 시 키 파일을 삭제하고 선택을 자동 분석으로 되돌린다.

Jev는 [공식 API 명세](https://api.typesafe.ai/openapi.json)에 따라 `https://api.typesafe.ai/v1/systemone`에 `jev-latest`와 5개의 Noul 질문을 한 번에 보낸다. 질문은 요청 충족, 대체 없는 검사 제거, 실패 후 복구, 중복 후속 확인, 결정에 영향을 주는 누락이다. 0.3~0.7 사이는 불확실로 유지하며 오류 응답을 판단으로 바꾸지 않는다. 이 판단은 독립적인 실행 검증이 아니다. 자유로운 설명문은 기존 Claude/Codex 분석을 선택해 사용한다.

질문창은 기본 너비 660px, 최대 높이 360px로 표시한다. 작은 모니터에서는 작업 영역에 맞춰 줄인다. 선택지를 가로로 배치하고 긴 내용은 스크롤하며 응답 버튼은 아래에 유지한다. 실제 Electron 질문·권한·응답 처리 통합 검사와 화면 캡처로 확인한다.

## 초기 비교와 재현 명령 (2.0.3 기준)

`analysis-pipeline-check.js`는 같은 합성 기록을 기존의 답변·도구 발췌 경로와 새 원문 준비 경로로 비교한다. 긴 도구 결과의 중간에 ‘질문 로그 노출 검사는 제거했고 대체하지 않았다’를 넣었다. 기존 발췌에서는 이 구절이 없고 새 경로에서는 회수된다. 이에 따라 전체 테스트 통과만으로 기존 검증 범위가 유지됐다고 볼 수 없다는 판단 근거가 생긴다.

삭제 후보 사례에서는 이전 `src/renderer` 사용처 확인 결과를 회수한다. 이미 확인한 범위를 반복 조사하는 대신 `reports API`나 `static`처럼 아직 확인하지 않은 범위를 구분할 수 있다. 이 설명은 모의 시험의 기대 판단이며 실제 모델 품질 입증과 구분한다.

로컬 측정 원본은 `artifacts/analysis-pipeline-benchmark.json`에 있고, 실제 Codex 반복 비교는 `artifacts/analysis-live-comparison.json`에 기록한다. 후자는 합성 기록만 사용하며 최종 표의 사례별 기존·개선은 각 1회라 대표 지연이나 일반적인 품질 향상을 주장할 수 없다. Jev의 실제 키를 사용하는 유료 API는 호출하지 않았다.

```sh
node scripts/terminal-review-test.js
node scripts/analysis-pipeline-check.js
node scripts/terminal-collaboration-test.js
node scripts/regression-test.js
node scripts/check-source.js
node_modules/.bin/electron scripts/terminal-workspace-check.js
node_modules/.bin/electron scripts/attention-popup-integration.js
# 실제 서비스 경로 비교: 합성 2사례 × 3회 × 기존/개선. 보정 시 호출 추가. 유료 호출:
node scripts/analysis-live-comparison.js --run
```

실제 모델의 단계별 시간·토큰·응답 비교와 검증 결과는 아래 실행 결과 절에서 구분한다. 이 절 아래는 배포 전 초기 실험 기록이다. 2.0.5 후속 검증은 별도 절에서 설명한다.

## 초기 실행 결과

| 합성 사례 | 기존 CLI 응답 | 개선 CLI 응답 | 기존 총 토큰 | 개선 총 토큰 |

| package-cleanup | 23.85초 | 31.72초 | 25,255 | 25,112 |

최종 비교의 모델 호출은 사례별 1회씩이며 모두 파싱·판단 검증을 통과했다. 합계 출력 토큰은 1,595에서 1,414로 줄었으나 전체 토큰은 50,452에서 50,376으로 약 0.15% 줄어든 정도다. 입력 토큰은 48,857에서 48,962로 소폭 늘었다. 전체 응답 시간은 50.82초에서 58.91초로 늘었다. 따라서 비용 절감이나 전반적인 속도 개선을 입증한 결과로 보지 않는다. 캐시 입력량도 실행 순서에 따라 달랐으며 금액으로 환산하지 않았다.

초기 비교에서는 삭제 후보에 생략된 로그를 다시 확인하라는 제안이 남았다. 확인·미확인·사용처가 긴 원문 가운데 있을 때도 보존하도록 발췌를 고쳤다. 생략 표시 자체를 사실 근거로 인용하는 응답도 검증에서 제외한다. 다음 시험의 삭제 후보 호출 1회는 180초에 타임아웃했다. 최종 시험은 중복 지시와 출력 반복을 줄인 요청 형식을 사용했다. 총 유료 Codex 호출은 8회이며 성공 7회, 타임아웃 1회다. 응답이 완료된 7회에서 확인된 총 토큰은 178,623이다. 타임아웃 호출의 토큰은 확인되지 않아 총 실험 비용은 확정하지 않는다. 이전 두 시험은 `analysis-live-comparison-initial.json`, `analysis-live-comparison-second.json`에 보존했다.

실제 분석의 차이:

- 패키지 정리: 기존 응답은 일반적인 변경·테스트 근거 재확인을 권했다. 개선 응답은 “20 passed는 대체 없이 제거된 로그 노출 검사의 역할을 대신하지 못한다”를 근거로, 제거된 검증을 먼저 회복하도록 다음 요청을 바꿨다.
- 삭제 후보: 기존 응답은 세 대상의 사용처를 다시 조사하도록 권했다. 개선 응답은 “ai-usage의 기존 사용처 확인은 코드가 그대로이므로 재사용할 수 있다”와 현재 미확인인 reports/static 범위를 나눠 다음 요청을 만들었다.
- 12개 보드 기반과 15개 잔여 패키지의 집합 관계를 구체적으로 설명하는 정도는 이번 응답에서 충분하지 않았다. 해당 숫자로 추가 삭제를 확정하지는 않았다. 다양한 작업에 대한 일반적인 판단 품질은 더 넓은 표본이 필요하다.

단계 측정의 해석:

- 실제 모델 비교는 프로세스 시작→첫 stdout→종료 시각, 준비·응답·파싱 시간을 기록한다. 이 시험에서 `firstResponseAt`으로 저장한 시각은 첫 stdout이다. 최종 제품 계측은 첫 stdout과 첫 공개 assistant 텍스트를 별도 필드로 구분하며, 알 수 없는 시각은 null로 남긴다.
- 기존 방식 첫 준비 시간에는 Git의 과거 모듈을 읽고 로드한 비용이 포함되어 새 방식과 직접 비교하지 않는다.
- 사용 모델명은 CLI 응답에 없었고 기본 모델 설정을 사용했다. 모델 버전과 캐시를 고정한 통제 실험이 아니다.
- 결과 이벤트와 역순 응답 방지는 Electron 테스트에서 확인했다. 모델 지연, 표시 지연과 전체 사용자 판단 시간을 같은 수치로 취급하지 않았다.

로컬 근거 준비는 합성 사례 5회에서 중앙값 2.51ms, 가장 느린 값 2.60ms였다. 로그 캐시 조회 중앙값은 0.06ms였다. 파일 크기·캐시·실행 환경이 제한된 작은 표본이며 p95나 전체 분석 속도의 추정치로 쓰지 않는다.

검증: `terminal-review-test`, `analysis-pipeline-check`, 협업 소켓/CLI 검사, 558개 회귀 검사, Electron 작업 공간 검사, 가로 질문창 통합 검사를 실행했다. 개별 검사 로그에는 실패를 재현하기 위한 offline/close 오류 fixture가 포함되어 있다. Jev 실제 키를 이용한 실서비스 연결, Windows 실행, 설치 앱 배포는 이번 검증 범위에 없다.


## 2.0.5 후속 성능 검증

Codex 분석 전용 호출은 기본 코딩 지침을 짧은 고정 지침으로 교체하고,
스킬 목록·앱 안내·협업 모드 안내를 전달하지 않는다. 셸·훅·에이전트·웹 검색 제한은
유지하고 MCP 및 클라우드 스킬도 비활성화한다. 일반 질문지와 사용자의 직접 실행에는
이 설정을 적용하지 않는다. 외부 CLI가 읽는 고정 지침은 `app.asar` 밖의 분석 전용
폴더에 원자적으로 쓴다. 지원 설정은 [공식 Codex 설정 명세](https://developers.openai.com/codex/config-reference)의
`model_instructions_file`, `skills.include_instructions`, `orchestrator.mcp`를 확인했다.

새 비교 스크립트는 불변 `v2.0.4`의 실제 `AgentRunner`와 `TerminalReview`를 불러오고,
새 코드의 같은 서비스 경로와 비교한다. 같은 명시 모델 `gpt-6.1-sol`, 같은 합성 기록,
같은 180초 호출 제한을 사용한다. 두 사례를 각 3회 반복하며 실행 순서를 바꾼다.
원문 준비, 인용 검증, 선택적 재조회와 최대 2회 형식 보정 경로를 포함한다.
`--resume`은 중간에 멈춘 동일 제품·모델 시험의 완료 표본만 재사용한다.
모델·입력 해시, 후보 소스 파일 해시, 각 유료 호출의 사용량과 오류를 남긴다.

원본은 로컬 `artifacts/analysis-speed-2.0.5-production.json`에 저장한다. 초기 지침 교체 시험과
직접 프롬프트 시험은 `analysis-speed-2.0.5.json`, `analysis-speed-2.0.5-final.json`에 따로 보존한다.
직접 프롬프트 시험은 실제 보정 호출 비용을 포함하지 않아 최종 성능 근거로 사용하지 않는다.
진행 중이던 해당 시험은 그 이유를 기록하고 소유 프로세스의 종료를 확인한 뒤 중단했다.
타임아웃과 중단 호출의 미확인 토큰은 0으로 계산하지 않는다.
표본이 작고 서비스·네트워크·캐시에 따라 변하므로 특정 표본의 감소율을 일반 SLA로 확대하지 않는다.
최종 수치와 배포 호환성 결과는 해당 릴리스의 검증 기록에 남긴다.


## 사용 한도 오류와 재시도 대기

실제 Codex 진단에서 `last status: 429 Too Many Requests`와 약 480초 후의
재시도를 확인했다. 이전에는 CLI가 기다리는 동안 Whitebox의 180초 제한이 먼저 끝나
일반 검토 시간 초과로 표시됐다. 내부 분석의 신뢰된 CLI stderr에서 이 진단을 확인하면
해당 분석 프로세스를 중지하고, 종료가 확인될 때까지 실행 슬롯을 점유한 채 추적한다.
모델이 출력하거나 터미널 기록에 인용된 429 문장은 이 경로를 실행하지 않는다.

같은 서비스의 대기 분석은 서버가 알린 시각까지 보존하고 화면에 사용 한도 대기와
남은 시간을 표시한다. 다른 서비스는 비어 있는 슬롯을 사용할 수 있다. 새로고침이나
직접 분석도 대기 시각을 앞당기지 않는다. 대기열과 서비스 대기 시각은 재시작 뒤에도
복구하며, 연속 3회 사용 한도 응답을 받으면 자동 재시도를 끝내고 명시적인 재요청을 기다린다.
결과를 받지 못한 호출의 토큰은 미확인으로 남기고, 앞서 확인된 사용량도 별도로 보존한다.

최종 서비스 비교 원본은 `artifacts/analysis-speed-2.0.5-verified.json`이다.
표본 사이에 60초를 두어 연속 실험의 사용 한도 영향을 줄이고 그 간격은 개별 분석 지연에
포함하지 않는다. 서비스가 새 대기 시각을 알리면 시험은 추가 호출 없이 중단한다.
